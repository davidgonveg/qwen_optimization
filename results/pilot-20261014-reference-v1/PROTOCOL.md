# Protocolo de fase 2A, versión 1

Fijado antes del piloto. Referencia intacta en `configs/reference.json`: mismo digest, Ollama 0.40.3, opciones, contexto 2048, techo de salida 256, semilla 42, think=false y concurrencia 1. No cambiamos MTP ni reparto. PowerShell/.NET existentes; sin dependencias Python.

Calidad: diez tareas originales españolas, zero-shot, orden y rúbricas en `pilot-v1.json`. Este conjunto es de desarrollo, separado de las cuatro pruebas de fase 1; tampoco será el conjunto final. Las siete tareas automáticas exigen respuesta exacta tras quitar únicamente espacio exterior o JSON semánticamente exacto (mismas claves, tipos y valores; sin bloques Markdown, comentarios ni claves duplicadas). Las otras tres se revisan con tres criterios binarios por tarea, evidencia textual y revisor identificado, sin LLM juez externo. No juntar esa rúbrica con la exactitud automática. Error, respuesta vacía o done_reason=length son fallos de fiabilidad; no se califican como éxito. Código guardado y leído, jamás importado/ejecutado. No es pass@1 ni IFEval/MMLU/GSM8K.

Rendimiento: prueba de compatibilidad como primera petición, con modelo no residente comprobado por /api/ps. Es observación de carga, sin vaciar caché de Windows, no entra en percentiles. Calidad con modelo residente. Después dos bloques, cada uno con un calentamiento excluido y cinco repeticiones. Contenido evaluado de rendimiento idéntico, cambia un identificador al comienzo del mensaje de usuario para el bloque variable; el bloque repetido mantiene petición idéntica. Ambos comparten plantilla de chat. No llamamos al bloque variable «sin caché»; guardamos el contador real de prefijo. El orden fijo puede confundir diferencias con deriva térmica. No es prueba sostenida ni experimento causal de aceleración. Máximo de salida igual a referencia; la instrucción pide salida breve, y se guardan los tokens reales y final anticipado.

Reloj Stopwatch monotónico desde envío: primer fragmento JSON, primer texto no vacío de reasoning y primer contenido visible por separado. TTFT es primer texto entregado al cliente (mínimo entre thinking/contenido), aproximado por fragmentos; no acceso al tiempo de token interno. Duraciones API en ns, cliente en s. Tokens/s salida = eval_count/(eval_duration/1e9). Velocidad de entrada sin caché = (prompt_eval_count - prompt_eval_cached_count)/(prompt_eval_duration/1e9), solo si ambos contadores existen y son coherentes. No atribuir tokens de thinking a un contador separado si la API no lo expone. Null significa desconocido. Contexto guardado desde /api/ps y log; no prueba de longitudes largas ni detector completo de truncamiento de entrada.

Telemetría reutilizada de fase 1 cada segundo nominal: GPU completa (MiB, W, °C, %), RAM Windows (KiB), árbol del servidor (bytes residentes y privados comprometidos, CPU acumulada en unidades 100 ns). Intervalo real y tiempo de colección guardados; CPU % del árbol se deriva de diferencias y se normaliza por procesadores lógicos. No se miden paginación, temperatura CPU, throttling, energía del PC ni respuesta del escritorio. Energía GPU aproximada por trapecios de potencia y tiempo entre muestras, abarca otros procesos y no resta reposo; se informa cobertura y gaps. Picos muestreados pueden perder máximos. Inventario inicial incluye procesos que usan GPU y /api/ps habitual. No se cierran procesos ajenos.

Resultados: directorio nuevo, copias de suite/config/protocolo, hashes de scripts y archivos de definición, revisión Git y estado de trabajo, petición, stream con tiempos, textos, métricas por petición, errores, /api/ps antes/después, inventario y log. Ningún reintento silencioso. Si hay fallo fatal queda run-status.json y datos parciales; no sobrescribir ni reutilizar RunId. Percentiles nearest-rank por condición exclusivamente sobre las cinco mediciones completas; n, fallos, tokens y caché individuales visibles. Con n=5 el p95 es solo el máximo. Coste para ampliar se estima a partir del tiempo medido, no presupuesto garantizado. No inferir calidad general ni mejora de una cuantización con este piloto.

Compatibilidad: [chat Ollama](https://docs.ollama.com/api/chat) documenta probabilidades de tokens generados, no puntuación forzada de una continuación arbitraria. La [interfaz de harness](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/model_guide.md) requiere esa continuación para loglikelihood. Se hace una petición real logprobs=true; aun si hay salida probabilística no demuestra compatibilidad con MMLU estándar. No instalamos harness ni datasets externos para este piloto. Fuentes consultadas el 14 de octubre de 2026 y resumidas en sources.json.
